v0.3.4 (2026-10-19)
--------------------
Bugfix: pořadí zápisů na zásobník podle Zilog UM0080

PUSH qq, PUSH IX/IY, CALL nn, CALL cc,nn, RST p a přijetí INT (IM 0/1/2)
i NMI zapisovaly na zásobník nejdřív nižší bajt. Zilog UM0080 u PUSH, CALL,
RST a NMI uvádí opačné pořadí: nejdřív vyšší bajt na SP-1, pak nižší na
SP-2 (IM 1 je "identické s NMI", IM 2 "provede CALL").

Oprava:
  - nové makro WR16_STACK v z80_execute.inc, používá ho makro PUSH
    (a tím CALL, CALL cc a RST),
  - přijetí INT a NMI v handle_interrupts_internal() používá nové
    wr16_stack_slow() místo wr16_slow().
WR16 (LD (nn),rr, nižší bajt dřív) a EX (SP),HL zůstávají beze změny.
Obsah paměti, počet zápisů i T-stavy jsou stejné jako dřív; mění se jen
pořadí volání callbacku zápisu do paměti (vidí ho např. záznam zápisů
nebo breakpointy na zápis). Týká se batch i per-step jádra.

Testy:
  - Nový tests/test_push_order.c (11 testů): PUSH BC, PUSH IX, CALL nn,
    CALL NZ,nn, RST 38h, přijetí INT v IM 0/1/2 a NMI (vyšší bajt dřív)
    a LD (nn),HL a LD (nn),BC (nižší bajt dřív). Bez fixu 9 z 11 testů
    selhává (ověřeno).
  - 463/463 unit testů PASS (452 -> 463).
  - ZEXALL 67/67 PASS přes obě jádra, nezměněný (3 785 306 090 T-stavů).
    Počet cyklů benchmarku nezměněný (2 214 609 436 T-stavů) ve všech
    režimech.

v0.3.3 (2026-10-14)
--------------------
Bugfix: z80_step() počítá délku kroku bez přetečení se znaménkem

z80_step() vracel délku instrukce jako rozdíl cpu->total_cycles (u32) před
a po kroku, ale obě absolutní hodnoty nejdřív převedl na int. Na hranici
2^31 to je přetečení se znaménkem, tedy nedefinované chování v C. Běžný
build vracel správné číslo náhodou; build s -ftrapv abortoval.

Oprava: rozdíl se počítá v u32 (modulo 2^32) a na int se převádí až malý
výsledek. Délka kroku je správná i při přetečení total_cycles na hranici
2^32. Týká se jen návratové hodnoty z80_step(); jádra, počítání cyklů
ani z80_execute() se nemění.

Testy:
  - Nový tests/test_step_cycles.c (3 testy): NOP přes hranici 2^31, NOP
    přes přetečení čítače na hranici 2^32, LD BC,nn přes obě hranice.
    S -ftrapv stará verze abortuje, nová projde.
  - 452/452 unit testů PASS (449 -> 452).
  - ZEXALL 67/67 PASS přes obě jádra, nezměněný (3 785 306 090 T-stavů).
    Počet cyklů benchmarku nezměněný (2 214 609 436 T-stavů) ve všech
    režimech.

v0.3.2 (2026-10-06)
--------------------
Bugfix: inkrement registru R během HALT a při přijetí INT/NMI

Jádro nezvyšovalo registr R při opakovaném fetchi HALT ani při potvrzení
maskovatelného přerušení (IM 0/1/2) a NMI. Na reálném Z80 je každé opakování
HALT (po 4 T, kvůli refreshi DRAM) M1 cyklus a přijetí INT i NMI začíná M1
cyklem s refreshem - v obou případech R += 1 (z80ex dělá totéž). Kód, který
čte LD A,R po HALT čekajícím na přerušení (např. loader odvozující
dešifrovací klíč z R), tak viděl jinou hodnotu než na reálném HW a mohl se
zacyklit.

Oprava:
  - halted větev v z80_execute.inc zvýší R (INC_R) za každé opakování HALT,
  - handle_interrupts_internal() zvýší R při přijetí NMI i INT
    (nová interní inc_r_on_int_ack()).
Mění se jen dolních 7 bitů, bit 7 zůstává. Týká se batch (z80_execute)
i per-step (z80_step) jádra a všech předchozích verzí (od v0.2).

Testy:
  - Nový tests/test_r_register.c (8 testů): opakovaný fetch HALT přes
    per-step i batch, zachování bitu 7, přijetí INT IM 1 z HALT, INT IM 2
    mimo HALT, NMI, nepřijaté INT pod DI (bez inkrementu navíc) a přijetí
    INT v batch jádru. Všech 8 testů bez fixu selhává (ověřeno).
  - 449/449 unit testů PASS (441 -> 449).
  - ZEXALL 67/67 PASS přes obě jádra, nezměněný (3 785 306 090 T-stavů).
    Počet cyklů benchmarku nezměněný (2 214 609 436 T-stavů) ve všech
    režimech.

v0.3.1 (2026-06-25)
--------------------
Bugfix: EI-delay v per-step jádře

Per-step jádro (z80_step) mazalo cpu->ei_delay v epilogu check_interrupts na
konci každého kroku. Po instrukci EI smazaný flag dovolil vstupnímu interrupt
checku PŘÍŠTÍHO kroku přijmout pending maskovatelné přerušení JEŠTĚ PŘED
instrukcí následující po EI - takže jednoinstrukční EI-delay byl v per-step
cestě fakticky nulový. U sekvence "EI; LD SP,nn" se přerušení přijalo před
LD SP a push návratové adresy šel na starý (neplatný) zásobník, čímž poškodil
paměť.

Oprava: epilog clear ei_delay je nově gateován #if !Z80_DIRECT_REGS. Batch
jádro (z80_execute) je beze změny - tam je clear potřeba, protože vstupní
clear běží jen 1x na dávku. Per-step ho vynechá a spolehne na vstupní clear
příštího kroku (ten běží před dispatchem instrukce po EI) -> přesně
jednoinstrukční EI-delay (replikuje noint_once z80ex jádra). Compile-time,
bez runtime větve; per-step navíc ušetří jeden zápis.

Týká se jen per-step jádra zavedeného v v0.3.0; batch cesta nebyla dotčena.

Testy:
  - Nový tests/test_ei_delay.c (5 testů): lifetime ei_delay, řetězení EI;EI,
    pending INT deferovaný přesně o 1 instrukci, regrese "EI; LD SP,nn"
    (push musí jít na NOVÝ zásobník) a guard že batch epilog ei_delay dál
    čistí. Regresní testy bez fixu selhávají (ověřeno).
  - 441/441 unit testů PASS (436 -> 441).
  - ZEXALL nezměněn přes obě jádra (3 785 306 090 T-stavů; ZEXALL načasování
    přijetí přerušení netestuje). Bez dopadu na výkon.

v0.3.0 (2026-06-22)
--------------------
Per-step jádro + volitelný RAM fast-path (bit-identické)

Dvě výkonová rozšíření, obě bit-identická s v0.2.7 (ověřeno: 436/436 unit
testů, ZEXALL přes OBĚ jádra - batch i per-step - a identický počet cyklů
2 214 609 436 ve všech režimech provádění). Veřejné chování i stávající
API jsou beze změny; jedna nová opt-in funkce (z80_set_ram_fastpath).

Per-step jádro (z80_step):
  Tělo execute smyčky bylo vyčleněné do sdíleného includu
  (cpu/z80_execute.inc) překládaného dvakrát z jednoho zdroje - žádný text
  handlerů se neduplikuje:
    - z80_execute() -> batch jádro: hlavní registry v C lokálech
      (RELOAD/WRITEBACK), prolog/epilog amortizovaný na celou dávku.
    - z80_step()    -> per-step jádro: registry jsou aliasy přímo na cpu->,
      žádná cache, žádný RELOAD/WRITEBACK. Odstraňuje per-call prolog/epilog
      registrové cache, když hostitel pohání CPU po jedné instrukci
      (cycle-accurate emulátory). z80_step() dříve volal z80_execute(cpu, 1)
      a platil ten prolog/epilog každou instrukci.

Volitelný RAM fast-path (-DCPU_Z80_RAM_FASTPATH, opt-in, default vypnuto):
  z80_set_ram_fastpath(cpu, read_table[16], write_table[16], dbus_latch,
  enabled) nainstaluje 16-položkovou page-table (1 / 4 KiB stránka, index
  addr>>12). RD/WR/FETCH na stránku čisté RAM (non-NULL ukazatel) jdou
  inline přes page[addr & 0x0FFF] místo memory callbacku; NULL stránky
  (mapped IO/ROM/contended) spadnou na mread_cb/mwrite_cb s plnou věrností
  vedlejších efektů i časování. Integrující vrstva tabulku přestavuje při
  každé změně bankingu. Vyplatí se POUZE když je memory callback drahý
  (reálná bankovaná paměťová mapa); při triviálním callbacku je to čistá
  režie (viz poznámky k benchmarku níže).

Výkon (poctivě, same-session microbenchmark vs z80ex-mz800, O2 průměr):
  z80ex-mz800 (per-step)            1072 MHz   1.00x
  cpu-z80 batch (z80_execute)       2822 MHz   2.63x
  cpu-z80 dispatch jádro            1123 MHz   1.05x
  cpu-z80 per-step (z80_step)       ~830 MHz   0.77x  (rozptyl běhů 750-870)
  cpu-z80 per-step + fast-path       627 MHz   0.58x

  Poznámky:
  - Batch (2.63x) NENÍ reprezentativní pro reálné použití: cycle-accurate
    emulátor synchronizující periferie uvnitř instrukce dávkovat nemůže.
  - "Dispatch jádro" = per-step jádro s vyloučenou obsluhou přerušení -
    fér srovnání s z80ex_step(), který také provádí jen opcode a přijetí
    přerušení nechá na volajícím. cpu-z80 computed-goto dispatch je tu
    ~5 % rychlejší než z80ex.
  - Plný per-step (z80_step) je pomalejší než z80ex_step, protože z80_step
    NAVÍC dělá interrupt check a post_step hook každou instrukci; z80ex_step
    ani jedno (přerušení řeší consumer). Propad je integrovaná funkčnost,
    ne pomalejší jádro.
  - Per-step + fast-path je TU pomalejší jen proto, že memory callback
    benchmarku je triviální (return ram[addr]); přínos fast-pathe se
    projeví až proti drahému callbacku.
  Často citované "2.8x" platí jen pro BATCH cestu. Viz
  docs/benchmark_*.txt pro plný rozpad a metodiku.

Testy / nástroje:
  - tests-zexall: nový per-step režim runneru (-DZEXALL_PER_STEP) žene
    ZEXALL přes z80_step; prochází se stejnými 3 785 306 090 T-stavy.
  - bench: nové cíle per-step, per-step+fast-path a dispatch jádro
    (make compare).
  - 436/436 unit testů PASS; počet cyklů 2 214 609 436 v batch, per-step
    i per-step+fast-path.

v0.2.7 (2026-06-01)
--------------------
Přesnost: PC během HALT drží adresu instrukce HALT

Reálný Z80 drží po celou dobu HALT PC = X = adresu instrukce HALT
(instrukce se re-fetchuje cyklicky kvůli DRAM refreshi; PC se
inkrementuje až těsně před skokem do INT/NMI rutiny). cpu-z80 dosud
nechával PC na X+1 (FETCH ho už inkrementoval) po celou dobu HALT,
takže observer čtoucí cpu->pc během HALT viděl nesprávnou hodnotu.

Týkalo se to jen POZOROVANÉ hodnoty PC během HALT. Hodnota uložená
na stack při INT/NMI accept i chování po návratu byly už správné
(X+1), protože inkrement se nyní děje při accept místo při fetchi.

Fix (tři zásahy, sémantika eventů beze změny):
  - op_76 (HALT): po HALT_ENTER eventu (ten dál vidí X+1) dekrementuj
    lokální PC zpět na X. WRITEBACK na konci instrukce ho propíše do
    cpu->pc.
  - NMI accept: pokud bylo CPU v HALT, inkrementuj cpu->pc na X+1
    před uložením návratové adresy.
  - INT accept: pokud bylo CPU v HALT, inkrementuj cpu->pc na X+1
    před HALT_EXIT eventem i pushem.

  HALT_ENTER / HALT_EXIT eventy dál vidí X+1, takže konzumenti
  cpu_ctrl_event nejsou dotčeni.

Pozn. ke konzumentům: tests-zexall/zexall_runner.c používal HALT
jako CP/M BDOS / WBOOT trap a počítal trap adresu jako `cpu->pc - 1`
(za předpokladu PC = X+1). Nyní čte `cpu->pc` přímo, v souladu
s opravenou sémantikou.

Testy:
  - Nový tests/test_halt_pc.c (6 testů): PC drží adresu HALT po
    HALT, PC zůstává přes kroky halt smyčky, NMI / INT-IM1 / INT-IM2
    z HALT všechny pushují X+1, a regression guard že INT mimo HALT
    není posunut was_halted cestou.
  - Existující HALT testy v test_interrupts.c a test_cpu_ctrl_event.c
    dál prochází (testují eventy / halted flag, ne during-HALT PC).
  - Celkový počet testů stoupl z 430 na 436.

Testy: 436/436 PASS, počet cyklů nezměněn (2 214 609 436).
ZEXALL: PASS, 3 785 306 090 T-stavů nezměněno (po úpravě trap
        adresy v runneru výše).
Bench: O2 ~2790 MHz, O3 ~2790 MHz. Same-session A/B vůči v0.2.6 je
       v rámci šumu - fix se týká jen op_76 a INT/NMI accept cest,
       z nichž žádná neběží v benchmark smyčce.

v0.2.6 (2026-05-20)
--------------------
Přidáno: CALL / RET dispatch hooky pro callstack subsystémy
  - z80_set_call(cpu, fn, data)
  - z80_set_ret(cpu, fn, data)

call_cb fire při každém taken CALL:
  - unconditional CALL nn (0xCD)
  - CALL cc, nn (0xC4 / 0xCC / 0xD4 / 0xDC / 0xE4 / 0xEC / 0xF4 / 0xFC),
    jen pokud je podmínka splněna (PC bude skutečně přesměrováno)

  Signatura callbacku: (cpu, call_site, target, return_addr, user_data).
  Fire timing: těsně před PUSH(rPC); rPC = target. V ten okamžik rPC
  už ukazuje za CALL opkód (FETCH16 cíle proběhl) a stack ještě
  nedrží return adresu. call_site = return_addr - 3 (3-bytové CALL).

ret_cb fire při každém taken RET:
  - unconditional RET (0xC9)
  - RET cc (0xC0 / 0xC8 / 0xD0 / 0xD8 / 0xE0 / 0xE8 / 0xF0 / 0xF8),
    jen pokud je podmínka splněna

  Signatura callbacku: (cpu, pop_target, sp_before_pop, user_data).
  pop_target se čte přes PEEK16(sp_before_pop) (rd16_slow bez
  op_tstate tiku - shoduje se s debug peek vzorem použitým jinde
  v jádře).

  RETI (ED 4D) ani RETN (ED 45) NEJSOU pokryty ret_cb. Lze je
  sledovat přes reti_cb a iff_change_cb (reason = RETI / RETN)
  resp. - interrupt-return callstack frame se má trackovat přes
  ty.

Vzor odpovídá v0.2.5 cpu_ctrl_event_cb. Hot path je jeden NULL ptr
check na call site; NULL = no-op, žádný měřitelný overhead.
z80_reset() oba callbacky call_cb i ret_cb zachová.

    RETI/RETN explicitně NEGENERUJOU ret_cb, a z80_reset() oba
    callbacky zachovává.
  - Celkový počet testů stoupl z 419 na 430.

Dokumentace:

v0.2.4 (2026-05-19)
--------------------
Přidáno: sjednocený callback změny IFF1/IFF2 pro debuggery a observery
         přerušovacího systému
  - z80_set_iff_change(cpu, fn, data)

Callback fire vždy když CPU modifikuje IFF1 nebo IFF2:
  - EI / DI instrukce
  - RETI / RETN
  - INT acknowledge (jakékoliv IM 0/1/2 - Z80 při ack INT vždy clearuje
    IFF1+IFF2 nezávisle na mode, liší se jen dispatchnutá rutina)
  - NMI acknowledge (IFF2 si zachová původní IFF1 aby RETN ho obnovil;
    reason NMI_ACK signalizuje sémantiku, ne nutně reálnou změnu IFF2)
  - CPU reset

Parametry: (cpu, new_iff1, new_iff2, reason, user_data). Reason je
jedna ze sedmi hodnot nového enumu z80_iff_change_reason_t (RESET /
EI / DI / INT_ACK / NMI_ACK / RETI / RETN), takže konzument může
rozlišit dispatch-driven IFF clear (INT_ACK / NMI_ACK) od explicit
instrukční změny (EI / DI / RETI / RETN).

Hot path: jeden NULL ptr check na všech call site. NULL = no-op,
žádný měřitelný overhead pokud callback nezaregistrován.
z80_reset() zachová iff_change_cb přes reset cyklus a po nastavení
nového stavu callback jednou fire s reason RESET.

Existující callbacky ei_cb / di_cb / nmi_cb / reti_cb / intack_cb
zůstávají beze změny - oba můžou koexistovat a fire pro stejnou
událost nezávisle, takže konzumenti, kteří už používají specifické
callbacky, fungujou bez úpravy.

Dokumentace:
  - API_en.txt / API_cz.txt 3.2 + 4.5 popisují nový reason enum,
    callback typ a setter.

Testy: 410/410 PASS, počet cyklů nezměněn (2 214 609 436).
ZEXALL: PASS, 3 785 306 090 T-stavů nezměněno.
Bench: O2 ~2902 MHz, O3 ~2937 MHz (v rámci šumu měření vůči
       baseline v0.2.3).

v0.2.2 (2026-05-19)
--------------------
Bugfix: ztracené zápisy registrů z callbacků za běhu instrukce
  - z80_execute() kešuje hlavní registry (A/F/B/C/D/E/H/L/PC/SP/WZ/R/Q)
    v lokálních proměnných. Když callback (mread/mwrite/pread/pwrite/

    instrukce, změna šla do cpu->...w, ale na konci instrukce ji
    WRITEBACK přepsal zpět starou hodnotou ze zastaralé lokální cache.
  - Fix: z80_execute() zaregistruje stack-allokovaný z80_local_cache_t
